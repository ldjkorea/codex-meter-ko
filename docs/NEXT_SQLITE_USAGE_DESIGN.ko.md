# Codex Meter NEXT — SQLite Usage Ledger 및 Insights 구현 설계

검증 기준: 2026-10-08, 기존 한국어판 `d2e2cf1`, 앱 `2.8.1 / 31`.

이번 상세 요청의 Phase 1/2는 이 문서의 구현을 따른다. [이전 JSON 원장 설계](NEXT_USAGE_DESIGN.md)는 초기 프로토타입의 기록이다. 해당 코드·Preference와 기존 차트 기록은 보존하며, 새 SQLite 원장이 장기 분석의 기준이 된다. [Phase 3 후속 명세](DESKTOP_TOKEN_ANALYTICS_SPEC.ko.md)는 설계만 작성했다.

## 1. 연결 구조와 보존 계약

`UsageApi.refreshAndCache(context)`의 기존 성공 경로에 선택적인 SQLite 관측 저장을 추가한다. 수동 버튼은 동일한 API의 `refreshAndCache(context, true)`를 사용한다. 서버 URL, 헤더, OAuth/PKCE, 토큰 저장, 기존 UsageParser/UsageWindow 정수 계산, 스냅샷, 자동 갱신 스케줄러와 위젯/Wear/Now Bar/AOD 경로는 그대로다. 기존 Reset Credit 부가 갱신도 그대로 실행한다. 자동 관측 때문에 추가 요청을 보내지 않는다.

원장 저장 오류는 고정 진단 코드로 기록하고 성공한 기존 새로고침을 실패로 바꾸지 않는다. 수동 기록은 조회 성공과 원장 저장 성공을 구분해 표시한다. DB 작업과 화면 조회·내보내기는 기존/새 작업 스레드에서 실행한다. `UsageLedgerDatabase`의 단일 잠금과 SQLite 트랜잭션으로 이관·저장·재집계·정리를 직렬화한다. 원장 요청으로 로그인이나 토큰 발급 흐름을 추가하지 않는다.

기존 Preferences 기반 원장/차트는 기존 동작을 위해 병행 기록한다. 새 화면의 통계 기준은 SQLite이며 서로 다른 저장소의 증가분을 합산하지 않는다. 초기 프로토타입은 로컬 체크포인트 `54893a6`으로 보존했다. 원본 9월 프로젝트와 원본 서명키는 수정하지 않는다.

## 2. 관측 데이터와 정밀도

- UTC 관측/예정 초기화 시각은 epoch milliseconds로 저장한다. 날짜 분류는 `Asia/Seoul`이다.
- `five_hour`, `weekly`, `monthly`와 추가 한도의 primary/secondary를 별도 meter로 보관한다. 없는 5시간 한도를 만들지 않는다.
- 추가 한도는 서버 식별 정보의 SHA-256 일부와 중복 순번/slot으로 구분한다. 원래 한도 이름/계정 정보는 저장하지 않는다. 알려진 분류에 없는 주 한도 창도 `additional:main:<slot>`으로 보관한다.
- `policy = meter | normalized_plan | window_seconds`. 같은 meter라도 플랜/창 길이가 다르면 소비량을 이어 계산하지 않는다. 이전 플랜으로 돌아와도 사이의 플랜 변경을 건너뛰지 않는다.
- 기존 화면은 기존 정수 사용률을 계속 사용한다. 별도 원장은 원 응답에서 해당 창과 일치하는 수치를 추출해 `REAL`과 decimal 문자열을 보존한다. 원 응답 전체는 보관하지 않는다. Android JSON 숫자 디코더/Double의 표현 범위 밖의 임의 정밀도까지 보장하지는 않는다.
- 잔여율은 `100 - used`로 파생한다. JSON/CSV에 사용률·잔여율을 함께 제공한다. 저장 중 두 수치가 서로 어긋날 여지를 줄이기 위해 잔여율을 중복 열로 저장하지 않는다.
- `source`: `api_precise`, `api_rounded`, `legacy`; `manual`: 수동 저장 요청 여부. API 관측은 취득 시점 fresh, 이관 기록은 freshness unknown이다. 현재 시점의 최신성은 기존 `UsageInsights.freshness`로 재평가한다.
- `UNIQUE(meter, observed_at)`로 동일 관측을 중복 저장하지 않는다. 새 수동 요청이 동일 관측을 가리키면 해당 행의 manual만 표시하고 별도 요청 시각을 남긴다. 같은 사용률이 다른 실제 시각에 관측되는 것은 유효한 관측이지만 소비량은 0이다. 기존 관측값을 새 값으로 덮어쓰지 않는다. 역순 응답은 거부한다.

## 3. SQLite 스키마 v1

새 앱 전용 DB 이름은 `codex_usage_ledger.db`다. 기존 의존성만 사용하는 `SQLiteOpenHelper`를 선택했다. Room/외부 DB/분석 SDK를 추가하지 않았다.

| 테이블 | 열/키 | 역할 |
| --- | --- | --- |
| observations | id PK; meter, plan, policy; observed_at, used, used_decimal, reset_at, window_seconds, source, manual; UNIQUE(meter, observed_at); 시간 index | 원시 관측 |
| daily | PK(policy, day); points, observations, first_at, last_at, covered_ms, uncertain_count, boundaries, legacy, quality | 서울 날짜별 관측 소비량 및 품질 |
| uncertain_intervals | PK(policy, start_at, end_at); points, reason | 날짜에 배분하지 않은 변화 |
| events | event_key PK; type, at, meter, origin | 관측 경계와 확인된 Reset Credit 동작 |
| manual_requests | observed_at PK; requested_at | 수동 요청 사실/성공 확인 |
| metadata | key PK, value | 이관 완료/명시적 삭제 tombstone, 마지막 마감 날짜 |

음수/100 초과 사용률, 잘못된 수동 플래그 등의 SQL CHECK와 Java 입력 검증을 함께 사용한다. 미래 DB 버전의 자동 파괴적 재생성은 하지 않는다. 지원하지 않는 업그레이드는 오류를 반환하고 DB를 보존한다.

## 4. 안전한 이관과 삭제

첫 DB 접근 시 기존 JSON 프로토타입을 먼저 읽고, 기존 5시간/주간/월간 UsageHistory를 추가로 읽는다. 동일 meter/시각은 중복 키로 제외하며, 프로토타입의 알려진 플랜을 우선한다. 차트에는 플랜 정보가 없어 `unknown`으로 이관한다. 모두 legacy로 표시하고 취득 시각을 변경하지 않는다. 기존 Preferences를 삭제·수정하지 않는다. 손상된 프로토타입은 그대로 보존하고 읽을 수 있는 차트 기록을 이관한다.

관측 insert와 `legacy_imported` marker는 같은 트랜잭션이다. 이관 실패 시 marker도 롤백되어 다음 접근에서 재시도한다. 모든 insert 실패 반환값을 확인하며, OR IGNORE의 실제 중복 키만 허용한다. CHECK/집계 쓰기/commit 실패를 저장 성공이나 이관 완료로 처리하지 않고 트랜잭션을 롤백한다.

첫 API 성공 시 기존 recorder가 방금 받은 응답을 먼저 Preference에 기록한다. 이 응답의 시각은 legacy 이관에서 제외하고 같은 트랜잭션의 실제 API 캡처로 저장한다. 따라서 첫 성공 응답의 소수 정밀도/최신성이 rounded legacy로 낮아지지 않는다. 원본 Preference의 해당 관측은 그대로 유지한다.

기존 `clearUsageHistory`와 `clearSnapshot`의 명시적 삭제/로그아웃 정책에 DB 정리를 연결한다. 관측·집계·이벤트·요청을 삭제하고 `legacy_imported=cleared` tombstone을 남겨 옛 데이터가 다시 이관되지 않게 한다. 새로운 삭제 흐름을 자동 실행하지 않는다. 개발/테스트 동안 설치된 앱의 사용자 데이터를 접근하거나 삭제하지 않았다.

삭제 시작 전에 별도 Preferences `codex_next_ledger_state/clear_pending`을 저장한다. DB 삭제 실패 시 다음 접근은 삭제를 먼저 재시도하고, 완료 전에는 원장을 읽거나 새 계정 기록을 추가하지 않는다. marker 제거도 commit 성공을 확인한다. 복구 마커에는 계정·인증 정보가 없다. 저장소 자체가 지속적으로 쓰기 불가능한 상황의 영구 삭제 완료는 보장할 수 없으며 오류로 처리한다. 사용자 기록 삭제는 인증 토큰을 삭제하지 않는다. 로그아웃의 인증 정리는 원래 흐름이 담당한다.

## 5. 집계와 경계 분류

같은 meter의 시각 순으로 이전 관측을 비교한다. 비교 불가능한 경계를 넘어 소비량을 계산하지 않는다.

| 분류 | 조건/의미 | 일별 소비량 처리 |
| --- | --- | --- |
| BASELINE | 첫 관측 | 증가량 없음 |
| NORMAL | 동일 policy/초기화 창, 유효 timeline, 6시간 이하 간격, 사용률 유지/증가 | 같은 서울 날짜면 증가량만 더함 |
| RESET | 이전 초기화 시각 이후 더 늦은 초기화 창 관측 | 초기화 전후 차감 안 함 |
| EARLY_WINDOW | 예정 전 새로운 창 또는 예상 밖 경계 | 원인 미확인; 증가분 합산 안 함 |
| CREDIT_CHANGE | 창/잔여량 변경 근처에 확인된 credit_used 동작 | 동작 확인과 해당 한도 인과관계를 구분; 합산 안 함 |
| CORRECTION | 동일 창에서 사용률 감소/잔여율 증가 | 보정 또는 원인 미확인; 음수 소비량 생성 안 함 |
| POLICY_CHANGE | 플랜/창 길이 변경 | 다른 policy로 분리 |
| GAP | 동일 창에서도 인접 관측 간격 6시간 초과 | 양의 변화는 미배분 구간으로 보존 |
| MISSING_TIMELINE | 유효 예정 초기화/시각 비교 불가 | 소비량 추론 안 함 |

NORMAL 구간도 날짜 경계를 넘으면 증가분을 양쪽 날짜에 나누지 않고 `date_boundary` 미배분 구간으로 보관한다. GAP의 같은 날짜 변화는 `measurement_gap`으로 보관한다. 조회 없는 날짜의 0을 생성하지 않는다. 각 날짜에는 실제 관측 수·첫/마지막 관측·측정 간격·미배분 구간 수·경계 수를 남긴다. 희소한 관측만으로 완전한 하루를 증명할 수 없으므로 모든 일별 기록은 `partial` 또는 `gap`이다. 소비량 단위는 `%p`, 실제 잔여율/사용률은 `%`다. 한도 간 퍼센트를 더한 총합은 없다.

확인된 credit_used/credit_expired/bank_increased는 기존 이벤트 저장소에서 가져오되 인증·credit ID를 포함하지 않는다. credit_used와 5분 이내의 한도 변화가 함께 관측되어도 특정 한도에 크레딧이 적용됐다는 인과관계를 확정하지 않는다. UI도 이 구분을 명시한다. 외부 발표/SNS 수집은 없다.

초기화 창별 통계는 연속 policy/창 구간의 NORMAL 증가분을 합한다. 긴 공백은 합산하지 않고, 계획 변경/감소/다른 경계에서 구간을 끊는다. 날짜를 넘는 정상 구간은 해당 초기화 창에는 속할 수 있지만 특정 날짜에는 배분하지 않는다. 표시값은 언제나 부분 관측이다.

## 6. 자정 마감·복구·보존

새 JobScheduler job `73120`은 서울 다음 날 00:01 이후/15분 deadline을 요청하는 최선 노력 로컬 집계 작업이다. 정확한 실행 시각을 보장하지 않는다. 추가 네트워크 호출·정확 알람 권한은 없다. 실패 시 JobScheduler 재시도를 사용하며, 성공 후 다음 날을 예약한다. 자동 성공 관측과 분석 화면 접근에서도 예약한다.

앱/기기가 중지되어도 다음 원장 접근 시 실제 관측을 재집계하고 `closed_through_seoul`을 어제로 갱신한다. 관측되지 않은 하루를 가짜 데이터로 메우지 않는다. 기존 자동 조회가 자정 근처에 성공하면 그 실제 시각을 기록한다. 별도의 자정 서버 조회는 추가하지 않았다.

- 원시 관측: 서울 날짜 기준 90일. 경계 재집계를 위한 meter별 직전 관측 1개를 추가 anchor로 유지한다.
- 일별 집계/미배분 구간/이벤트/수동 요청 사실: 750일, 최소 2년 목표를 충족한다.
- 매 정리에서 원시 기록을 지우기 전에 일별 집계를 저장한다. raw horizon 안은 재계산하고, 그 이전의 저장된 집계는 덮어쓰지 않는다. 따라서 raw 정리나 재시작으로 일별 통계가 사라지지 않는다.
- retention은 원장 접근/마감 시 실행된다. 앱이 실행되지 않는 동안 만료 행이 즉시 지워진다는 보장은 없다. 저장량은 실제 조회 주기에 비례한다. 분 단위의 극단적인 장기 조회량에 대한 성능/용량 실측은 기기 검증 과제다.

## 7. 화면·예측·급증 안내

메인 화면 기존 사용 기록 카드에 오늘 관측 소비량 한 줄과 상세 분석/현재 사용량 저장 진입을 추가한다. 자세한 통계는 `LedgerAnalyticsActivity`로 분리한다. 기존 테마/Ui 구성 요소와 언어 리소스를 사용한다.

분석 화면: 독립 한도/policy 선택, 일간·7일·30일 전환, 오늘/어제, 선택 기간 관측 합/공백 날짜, 막대 추세, 날짜별 상세, 750일 범위 이동 가능한 달력 히트맵, 최근 초기화 창/이벤트/미배분 구간, CSV/JSON 내보내기. 없는 날짜는 측정 공백이며 0 막대로 보간하지 않는다. 상세 팝업은 원시 100개까지 표시하며 전체 보존 기록은 내보내기에서 제공한다. 초기화 창/이벤트/미배분 카드는 가독성을 위해 최근 5/20/12개를 표시한다.

기존 `UsageInsights`의 freshness/기간/최대 공백 조건과 `UsageWindow.sameResetWindow`를 재사용한다. `LedgerForecast`는 최근 24시간의 연속·동일 policy/초기화 구간을 검사한다. 오래된 마지막 자료, 미래 시각, 지난 초기화, legacy 최신 자료, 플랜 변경, 긴 공백, 사용률 감소, 한 번에 30%p 초과 증가에서 예측을 보류/구간을 끊는다.

| 조건 | 5시간 및 8시간 이하 추가 창 | 주간/월간/긴 추가 창 |
| --- | --- | --- |
| 최소 관측 | 3 | 3 |
| 최소 기간 | 10분 | 6시간 |
| 최대 인접 공백 | 1시간 | 6시간 |
| 최소 증가 | 2%p | 2%p |

속도는 관측 증가량 / 경과 시간, 일일 예산은 최신 잔여량 / 초기화까지 시간의 일 단위 값이다. 예산은 최신 잔여량을 초과하지 않게 제한한다. 신선한 관측과 유효 초기화 시각만 있으면 계산할 수 있으므로 속도 예측에 필요한 기록이 부족해도 예산은 표시한다. 오래된 관측의 현재 예산은 보류한다. 예상 소진 시각/초기화 시 잔여율은 최근 속도가 계속된다는 선형 가정이며 실측값과 구분한다. 신뢰구간·AI 엔진·프로젝트별 비용을 만들지 않는다.

급증은 충분한 두 관측 구간의 속도 비율 2배 이상일 때만 안내한다. 각 구간도 최소 기간과 증가 조건이 필요하다. 옵션 기본값은 꺼짐이며 화면 내 안내만 제공한다. 새 푸시/알림 채널을 만들지 않아 반복 푸시가 없다. 작업 가능성 가이드는 관측 주간 잔여율/관측 시각/초기화 일정/남은 시간과 추정 속도·위험을 보여준다. 충분한 구간이 있을 때 이전 관측 구간 대비 속도 비율을 표시하며, 급증 안내 옵션과 분리한다. 프로젝트 작업 비용은 산정하지 않는다.

## 8. 내보내기/검증 경계

Android Storage Access Framework의 사용자가 선택한 문서 URI에 UTF-8 CSV/JSON을 쓴다. 별도 서버/공유/업로드 기능은 없다. 트랜잭션으로 읽은 스냅샷을 내보낸다. 원시 관측, 750일 일별 집계, 미배분 구간, allowlist 이벤트만 제공한다. 계정 ID·인증 토큰·원 응답·대화·프로젝트·파일 경로를 포함하지 않는다. CSV는 quote/CRLF escape와 formula 시작 문자 보호를 적용한다. JSON schema_version=1, 날짜 시간대/단위를 명시한다. raw가 정리된 오래된 날짜에는 일별 집계만 있고 관측을 재생성하지 않는다.

순수 Java로 실제 캡처/집계/예측/내보내기를 검증하고, 생산 DAO를 JVM Android API fixture 및 Python 표준 SQLite에 연결해 실제 SQL/트랜잭션/이관/재개방/보존/오류 복구를 검증한다. 이 테스트는 Android SQLite 런타임, 화면 렌더링, SAF 제공자, Doze/job, 실제 OAuth/API, 시스템 표면의 기기 검증을 대신하지 않는다. 실행 결과와 APK 증거는 [완료 보고서](NEXT_SQLITE_COMPLETION_REPORT.ko.md)에 기록한다.
